# CI/CD & Deployment Conventions

## GitHub Actions
- CI: 7개 독립 병렬 job (`lint`, `type-check`, `test`, `build-cli`, `rust`, `swift-build`, `swift-smoke-ios`) — 앞 5개는 ubuntu-latest, `swift-build`/`swift-smoke-ios`만 macos-26. Per-job steps/toolchain/캐시 메커니즘은 `.github/workflows/ci.yml` 인라인 코멘트가 SoT — 여기서 반복하지 않는다.
- **clippy step 에 `-- -D warnings` 를 절대 붙이지 않는다** — 그 플래그는 pedantic 그룹(~125 warning)까지 error 로 over-promote 해 빌드를 깬다. 린트 심각도 SoT는 `rust/Cargo.toml`의 `[workspace.lints]`(`clippy::all=deny`, `clippy::pedantic=warn`).
- **로컬 전용 real-claude E2E(`TP_E2E_CLAUDE*`)는 `swift-smoke-ios` job 에서 절대 돌지 않는다** (credential-free, 결정론적 loopback 사용).
- **Required status checks** (Ruleset 14604664, live): `lint`/`type-check`/`test`/`build-cli`/`rust` 5개가 필수 merge gate (`rust` 는 안정 green 확인 후 이미 승격됨). `swift-build` 와 `swift-smoke-ios` 는 아직 **non-required** — main에서 안정적으로 green 확인 후 required 목록에 추가한다 (없는 context를 required로 걸면 모든 PR이 wedge — 그래서 신규 job 은 항상 non-required 로 먼저 들어간다). **merge method = squash-only** (ruleset 강제 — 3종 merge 중 squash만 허용).
  - **PR3(#5 cascade) 가 이 5개 job body 를 Bun→Rust 로 스왑하면서 job KEY(=context 이름)는 바이트 단위로 보존했다** — GitHub 은 required context 를 job id 로 매칭하므로 이름만 유지하면 body 를 통째로 바꿔도 ruleset 을 건드릴 필요가 없다. **required job 에 job-level `name:` 을 절대 추가하지 않는다**(붙이면 context 가 job id 와 어긋나 orphan → 그 required context 가 영구 pending 으로 남아 모든 PR 이 wedge). 이름 rename 도 동일 파국이라 금지.
- Secrets: `RELAY_HOST`, `RELAY_USER`, `RELAY_SSH_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`

## Release (`release.yml`, triggered on `v*` tag push or manual `workflow_dispatch -f tag=vX.Y.Z`)
- tag-push event 는 GitHub API tag-creation 시 누락되는 케이스가 잦아 (#172) **항상 manual dispatch 로 트리거**: `gh workflow run release.yml -f tag=vX.Y.Z`
- Release Please: Conventional Commits → 자동 version bump + CHANGELOG → PR
- Tag prefix: `v*` (e.g. `v0.1.13`) — `release/v*` is legacy, removed in PR #96
- 수동 편집 금지: version 필드는 Release Please가 관리
- **빌드 job 2개(darwin/linux, Rust-only 번들) + publish 절차**는 `.github/workflows/release.yml` + `scripts/build-bundle.sh` 인라인 코멘트가 SoT — 여기서 반복하지 않는다.

- TestFlight job(archive/서명/업로드) 메커니즘은 `.github/workflows/testflight.yml` 인라인 코멘트 + `ios/project.yml` 가 SoT — 여기서 반복하지 않는다.
- **[ASC 90967 — AppIconVision `solidimagestack` Back layer]**: `AppIconVision.solidimagestack` 의 각 `.solidimagestacklayer/Content.imageset` 은 **1x(512×512) + 2x(1024×1024) 두 항목 모두** 필요 — 2x 만 빠지면 ASC 가 error 90967 "must contain a background layer with a scale value of 2" 로 업로드를 거부한다. actool 은 로컬에서 1x-only 를 조용히 통과시키므로 actool 로는 이 ASC 요구사항을 로컬 감지 불가. 세 레이어 모두 `icon-layer-{back,middle,front}@2x.png` (1024×1024, hasAlpha:no) 를 포함하고 Contents.json 에 `scale: 2x` 항목을 추가한다 (PR #808 이후 fix).
- 서명은 항상 일회용 keychain(`$RUNNER_TEMP/tp-signing.keychain-db`)에서만 이뤄진다 — 러너 login keychain 은 절대 건드리지 않는다 (`always()` step 으로 keychain+프로필+키 정리).
- **archive 경로의 STDOUT 은 아티팩트 경로 한 줄만 — 빌드 도구의 stdout 누수가 `$GITHUB_OUTPUT` 을 깬다 (런 28326191287 `Unable to process file command 'output'` / `Invalid format '⚙️  Generating project...'` 수정).** 워크플로는 `IPA="$(TP_PLATFORM=ios scripts/ios.sh archive)"` 로 `cmd_archive` 의 stdout 을 캡처해 `echo "ipa=$IPA" >> "$GITHUB_OUTPUT"` 하므로, `cmd_archive` 와 그 호출 사슬(`ensure_xcframework`→`cmd_rust`→`build-xcframework.sh`, `ensure_project`→`cmd_gen`) 전체가 stdout 에 **오직 최종 `.ipa`/`.pkg` 경로** 만 남겨야 한다 — 그 외 한 바이트라도 새면 `$GITHUB_OUTPUT` 의 `key=value` 형식이 깨져 archive+export 가 성공해도(=`.ipa` 생성) job 이 output 캡처 단계에서 fail 한다. 누수원 2곳을 stderr 로 리다이렉트: (1) `cmd_gen` 의 `xcodegen generate` 가 stdout 으로 찍는 `⚙️  Generating project...`(`scripts/ios.sh` `cmd_gen` → `( … xcodegen generate ) >&2`), (2) `build-xcframework.sh gen_bindings` 의 `cargo run --bin uniffi-bindgen`(=`cargo run` 이 자식 바이너리 stdout 을 forward — `( … cargo run … ) >&2`). `cargo build` 와 `xcodebuild`(`| xcbeautify_or_cat >&2`)·`-create-xcframework`(`>&2`)·`log()`(`>&2`)·`die()`(`>&2`)·`PlistBuddy`(파일/`>/dev/null`) 는 이미 stdout-clean. **검증**: `out="$(TP_FORCE_RUST=1 scripts/ios.sh rust 2>/dev/null)"; [ -z "$out" ]` 및 `out="$(scripts/ios.sh gen 2>/dev/null)"; [ -z "$out" ]` — 둘 다 0바이트여야 한다.
- **빌드 번호**: `TP_BUILD_NUMBER=$(( RUN_NUMBER * 100 + RUN_ATTEMPT ))` → `cmd_archive` 가 `CURRENT_PROJECT_VERSION` 오버라이드(ASC 는 재사용 빌드번호 거부, 단조 증가 필수). `run_number*100+run_attempt` 는 run 마다 단조 증가 + "Re-run failed jobs" attempt 마다 유니크 → 업로드 성공 후 재실행이 ASC 의 이미-사용된 CFBundleVersion 과 충돌 안 함. **산술은 반드시 셸 `$(( ))` 에서**
- **`CFBundleVersion`/`CFBundleShortVersionString` = 반드시 변수 참조 (ASC 중복 버전 거부 방지)**: 메인 `Teleprompter` 타깃은 `GENERATE_INFOPLIST_FILE=YES` 와 함께 **명시적 `INFOPLIST_FILE=Teleprompter-Info.plist`** 도 설정한다 — scene manifest + CFBundleURLTypes 를 담기 위해 필수. XcodeGen 이 이 plist 를 `info: properties:` 블록에서 생성할 때, 변수 참조 없이 냅두면 `CURRENT_PROJECT_VERSION` 의 **리터럴값("1")** 이 `CFBundleVersion` 에 구워진다 — 그러면 archive-time `CURRENT_PROJECT_VERSION=<TP_BUILD_NUMBER>` 빌드세팅 오버라이드가 명시적 plist 값에 의해 덮여 효과가 없다. 결과: 모든 TestFlight 빌드가 CFBundleVersion=1 을 출하 → ASC 가 두 번째 업로드부터 "bundle version must be higher than … '1'" 으로 거부. **(run 28333992407 에서 iOS TestFlight 업로드 실패 — 동일 레이턴트 버그가 macOS/visionOS 다음 업로드도 차단할 예정이었음)**. 수정: `ios/project.yml` 의 `info: properties:` 블록에 `CFBundleVersion: "$(CURRENT_PROJECT_VERSION)"` + `CFBundleShortVersionString: "$(MARKETING_VERSION)"` 를 변수 참조 문자열로 선언 → XcodeGen 이 참조를 plist 에 그대로 기록 → xcodebuild 의 `ProcessInfoPlistFile` 단계에서 빌드세팅 값으로 치환. **`GENERATE_INFOPLIST_FILE=YES`** 를 쓰는 `TeleprompterWatch` 타깃(명시적 `INFOPLIST_FILE` 없음, `info:` 블록 없음)은 이 문제가 없다 — Xcode 가 plist 를 직접 생성하며 항상 빌드세팅 값을 주입한다. 수정 범위는 명시적 INFOPLIST_FILE 이 있는 메인 타깃만. — GitHub Actions expression 에는 산술 연산자(`* + - /`)가 없어 `${{ github.run_number * 100 + github.run_attempt }}` 는 워크플로 **파싱 에러**(`*` unparseable)를 내 모든 브랜치 push 가 0-job red run 을 찍는다. `run_number`/`run_attempt` 는 정수 컨텍스트 조회라 env 로 주입 후 `$(( ))` 에 안전히 전개. 버전 문자열은 `project.yml MARKETING_VERSION`.
- **export-compliance**: `project.yml` Info.plist 에 `ITSAppUsesNonExemptEncryption: false`(표준 XChaCha20/X25519 = EAR 740.17(b)(1) 면제) — 없으면 TestFlight 가 "Missing Compliance" 로 빌드를 테스터에게 안 풀어줌.
- **macOS 전용 entitlements (ASC 오류 수정, 런 28332635131)**: macOS 앱은 `ios/Teleprompter-macOS.entitlements` 에 `com.apple.security.app-sandbox=true`(ASC 오류 90296 필수 — 없으면 "App sandbox not enabled") + `com.apple.security.network.client=true`(sandbox 내 아웃바운드 WebSocket 허용 — 없으면 릴레이 연결 불가)를 선언하고, `project.yml` Info.plist 에 `LSApplicationCategoryType=public.app-category.developer-tools`(ASC 오류 90242 필수 — 없으면 "Info.plist must contain LSApplicationCategoryType")을 포함한다. **로컬 ad-hoc macOS smoke 는 영향 없음** — `scripts/ios.sh` 의 macOS build/smoke 경로가 `CODE_SIGN_ENTITLEMENTS=""`(lines 509, 1790)로 entitlements 파일을 완전히 무시하므로 sandbox 키가 있어도 로컬 `-` 서명 빌드가 깨지지 않는다. `LSApplicationCategoryType` 는 iOS/visionOS 에서 harmless(optional key, AppKit 처럼 무시됨)하므로 per-platform plist split 불필요.
- **시크릿 게이트**: `guard` job(ubuntu)이 필수 시크릿 존재를 output 으로 노출, `archive-and-upload` 가 `needs.guard.outputs.ready=='true'` 일 때만 실행 — **포크/시크릿-없는 환경에서 skip(`::notice::`), PR wedge 안 함**. 필요 시크릿: `IOS_DIST_CERT_P12_BASE64`, `IOS_DIST_CERT_PASSWORD`, `IOS_PROVISIONING_PROFILE_BASE64`, **`IOS_WATCH_PROVISIONING_PROFILE_BASE64`**(임베드 watch 앱 profile, hard-required — guard 가 없으면 skip), `ASC_API_KEY_P8_BASE64`, `ASC_API_KEY_ID`, `ASC_API_ISSUER_ID`, `APPLE_TEAM_ID`.
- **번들 ID = `dev.tpmt.app`** (구 Expo 앱과 동일 — ADR-0004 §3 의 "구 레코드 재사용" 선택). 이 ID 를 유지하면 구 Expo 앱이 쓰던 동일 ASC 레코드/TestFlight 채널에 새 빌드로 올라간다(채널 연속성). 파이프라인은 번들 ID 무관(`PRODUCT_BUNDLE_IDENTIFIER` 가 SoT) — 새 레코드로 가려면 `project.yml` 의 ID 를 바꾸면 됨. APNs 토픽(`APNS_BUNDLE_ID`)은 번들 ID 와 일치해야 하므로 `dev.tpmt.app` 이어야 함.
- **watchOS 배포 — iOS 잡에 통합 (ADR-0004 Amendment 2, #123)**: watchOS 는 더 이상 별도 `guard-watchos` / `archive-and-upload-watchos` 잡이 없다. `TeleprompterWatch` 는 **메인 iOS 앱에 컴패니언으로 임베드**돼 iOS `.ipa` 에 동반 출하된다 (`Payload/Teleprompter.app/Watch/`). `ios/project.yml` 의 `Teleprompter` 멀티플랫폼 타깃이 `- target: TeleprompterWatch / embed: true / destinationFilters: [iOS]` 를 가져 "Embed Watch Content" copy-phase 가 iOS 슬라이스에만 활성화된다(macOS/visionOS 슬라이스는 스킵, `platformFilters = (ios,)` — BUILD SUCCEEDED 경험적 확인). 번들 ID: `dev.tpmt.app.watchkitapp`(구 컨테이너 `dev.tpmt.app.watch` + watchkitapp `dev.tpmt.app.watch.watchkitapp` 에서 2→1로 통합). `WKCompanionAppBundleIdentifier` = `dev.tpmt.app`, `WKRunsIndependentlyOfCompanionApp=YES` / `WKApplication_IsIndependentApp=YES` **유지** (컴패니언 배포 + 독립 런타임 병존). ASC 레코드 2 → 1(`dev.tpmt.app` 단일 레코드가 watch 슬라이스 포함). **iOS `archive-and-upload` 잡이 watch 빌드를 흡수**: (a) nightly Rust + `rust-src` 설치(arm64_32 watchOS `-Z build-std` 슬라이스 빌드에 필요), (b) `xcodebuild -downloadPlatform watchOS`(watch SDK 확보; Apple SDK CDN 의 간헐 exit 70 flake 에 대비해 3회 백오프 재시도 — run 28578680851 attempt 1 이 여기서 죽고 rerun 은 13초에 통과), (c) iOS 앱 profile + **임베드 watch 앱 profile(`IOS_WATCH_PROVISIONING_PROFILE_BASE64`)** 둘 다 keychain 에 설치. 인증서는 iOS Distribution 재사용, `altool --type ios`(watch 슬라이스는 서버가 watchOS App Store 로 라우팅). (d) **`TP_FORCE_RUST: "1"` 을 archive step env 에 설정 (#125, BLOCKER 수정)** — `TpCore.xcframework` 는 `rust/target/` 아래(ios.sh:114)에 있고 `Swatinem/rust-cache(workspaces: rust)` 가 그 디렉터리를 캐시한다. ci.yml 의 swift-build/swift-smoke 잡이 `TP_SKIP_ARM64_32=1` 로 빌드한 **6-슬라이스(watch device arm64-only, arm64_32 없음)** xcframework 가 캐시에 저장되는데, 그게 복원되면 `ensure_xcframework()` 가 Info.plist 존재만 보고(슬라이스 완전성 미검사, ios.sh:401/411) **재빌드를 스킵** → 임베드 watch 가 필요한 iOS **device** archive 가 `missing architecture(s) ... arm64_32` 로 **runner 프로비저닝+키체인 셋업 후** hard-fail(유료 분 낭비). `TP_FORCE_RUST=1` 이 7-슬라이스(arm64_32 nightly `-Z build-std` 포함) 를 강제 재빌드해 poisoned cache 를 무시한다. 인증서는 iOS Distribution 재사용, `altool --type ios`(watch 슬라이스는 서버가 watchOS App Store 로 라우팅). **non-required.** `ios/ExportOptions.watchos.plist` 삭제됨.
- **macOS/visionOS archive 잡은 `TP_SKIP_ARM64_32: "1"` 을 archive step env 에 설정해야 한다 (런 28318333155 에서 둘 다 `nightly rust-src missing` 으로 fail 한 버그 수정).** 이 두 잡은 watch 를 임베드하지 않으므로 archive 에 macos-fat/xros 슬라이스만 쓰지만, `build-xcframework.sh` 는 `TP_PLATFORM` 과 무관하게 **항상 9 슬라이스 전부**를 빌드하려 한다 — 그 중 watchOS-device 의 arm64_32 sub-슬라이스는 Rust tier-3 라 nightly toolchain + `rust-src`(`-Z build-std`)가 필요하다. iOS 잡은 watch 를 임베드하므로 nightly+rust-src 를 설치하지만 (위 (a)), macOS/visionOS 잡은 stable 1.96.0 만 설치하므로 `ensure_nightly()` 가 `nightly rust-src missing` 으로 die 한다 (`build-xcframework.sh:97-99`). `TP_SKIP_ARM64_32=1` 이 `build_watchos_arm64_32()` 의 nightly 경로를 건너뛰게 한다 (`build-xcframework.sh:131-135`) — 이 한 sub-슬라이스만 빠진 xcframework 는 macOS/visionOS archive 에 전혀 영향이 없다 (watch-device 슬라이스를 안 쓰므로). iOS 잡엔 절대 설정하지 않는다 (arm64_32 가 임베드 watch device archive 에 필수).
- **non-required** (신규 job 규율 — 안정 green 후 승격). 플랫폼별 job(iOS/macOS/visionOS) 전부 non-required 로 진입 (watchOS 는 iOS 잡에 통합, 별도 job 없음). **5플랫폼 TestFlight 스캐폴딩 완성** — 시크릿/ASC 레코드가 채워지면 release 마다 `release.yml` 의 `testflight` job 이 자동 dispatch 해 전 플랫폼 업로드(위 "트리거 (CD primary path)"). 첫 업로드는 수동(`gh workflow run testflight.yml -f tag=...`, Task #122) — Apple 계정 필요.

## Relay Deploy (`deploy-relay.yml`, ADR-0003 Step 8b — Rust 바이너리)
- **빌드/배포/시크릿 관리** 메커니즘(Rust 빌드, SCP 배포, drop-in secrets, 트리거 경로)은 `.github/workflows/deploy-relay.yml` 인라인 코멘트가 SoT — 여기서 반복하지 않는다.
- **arm64 호스트 전환 시 주의**: `ubuntu-latest`(x86_64)에서 `aarch64-unknown-linux-gnu` 링크는 `gcc-aarch64-linux-gnu` 크로스 링커가 필요(현 워크플로우 미설치) — 현 Vultr 가 x86_64 라 dead path 지만 전환 시 `cross`/링커 추가 필요.

- `scripts/build-bundle.sh <suffix> <rust-target>`: release 번들 빌더 (PR6 에서 구 `scripts/build.ts` Bun compile 대체) — cargo 4-bin release 빌드 → prefix-tree 조립(`bin/tp` + `libexec/tp/{tp-daemon,tp-relay,tp-runner,tpd-stub}`) → `dist/tp-<suffix>.tar.gz`. Native Windows is unsupported — Windows users run the Linux build under WSL.
- `scripts/install.sh`: curl-pipe-sh installer (macOS/Linux; Windows users run inside WSL)
- (구 `scripts/deploy-relay.sh` 수동 SSH 배포 스크립트는 PR6 에서 삭제 — Bun 단일 바이너리 `dist/tp-linux_*` + `ExecStart=tp relay start` 레이아웃을 전제해 현행 `tp-relay` 별도-바이너리/drop-in 구조와 충돌. 수동 relay 배포 = `deploy-relay.yml` dispatch)
